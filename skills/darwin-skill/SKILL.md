# Darwin Skill for OpenClaw

这是 `alchaincyf/darwin-skill` 的 OpenClaw 适配版。

保留原始思想，但改写为更适合当前环境的执行方式：
- 以 OpenClaw workspace 为主
- 优先使用本地文件与 OpenClaw 会话能力
- 强调人类确认，不做失控式自动修改
- 默认面向 skill 文件本身，不擅自扩展到安装依赖或大规模重构

## 适用场景

当用户表达以下意图时触发：
- “优化这个 skill”
- “这个 skill 写得不太行，帮我改改”
- “评估一下 skills 的质量”
- “给这个 skill 打个分”
- “自动迭代一下这个 skill”
- “检查一下这个 skill 有没有问题”

如果只是普通文案微调、补一两句描述、改个路径，不必动用完整 Darwin 流程。

---

## 核心原则

### 1. 单一目标
每次只处理一个目标 skill，避免多 skill 同时修改导致归因混乱。

### 2. 先评估，再修改
不能上来就改。先建立 baseline，知道问题在哪，再做修改。

### 3. 每轮只改一个主要问题
一轮只针对一个最低分维度或一个最明显缺陷，避免多变量同时变化。

### 4. 验证独立于编辑
能用独立会话/子 agent 验证时，优先独立验证，避免“自己改自己夸”。
如果条件不允许，至少做 dry-run 推演，并明确标注。

### 5. 人在回路
涉及真实保留的改动时，展示摘要、分数变化和关键 diff，再由用户决定是否继续扩大范围。

### 6. 可回滚
所有改动都应可逆。优先小步编辑，必要时借助 git 记录，但不要为了走流程强行引入新依赖。

## 评估维度（8维，总分100）

### A. 结构维度（60分）

1. **Frontmatter 质量**（8）
   - 名称清晰
   - description 说明“做什么 + 什么时候用”
   - 不空泛

2. **工作流清晰度**（15）
   - 步骤有顺序
   - 每步可执行
   - 输入输出明确

3. **边界条件覆盖**（10）
   - 有失败分支
   - 有 fallback
   - 没把复杂情况直接跳过

4. **检查点设计**（7）
   - 关键决策前有人类确认
   - 不会导致 agent 自主失控

5. **指令具体性**（15）
   - 不模糊
   - 有具体动作
   - 必要时带格式或示例

6. **资源整合度**（5）
   - 引用路径存在
   - 相关文件能访问
   - 没引用失效资源

### B. 效果维度（40分）

7. **整体架构**（15）
   - 层次合理
   - 不重复
   - 和 OpenClaw / ClaWiser 工作方式兼容

8. **实测表现**（25）
   - 用 2 到 3 个典型 prompt 验证
   - 比不带 skill 的 baseline 更好，或至少更稳
   - 没引入明显副作用

### 评分规则
- 每项按 1 到 10 分打分
- 最终总分 = Σ(单项分 × 权重) / 10
- 改后分数必须**严格高于**改前，才算有效改进

## 标准流程

### Phase 0：确认范围
1. 确认目标 skill 路径
2. 确认是“只评估”还是“评估 + 改进”
3. 如果是批量任务，先按优先级选 1 到 3 个，不要一口气全改

### Phase 0.5：设计测试 prompt
为目标 skill 设计 2 到 3 个测试 prompt：
- 一个典型主场景
- 一个稍复杂场景
- 一个容易出问题的边界场景（可选）

把测试 prompt 明确写下来，避免改前改后测的不是同一件事。

### Phase 1：建立 baseline
1. 读取 SKILL.md
2. 按 8 维度评分
3. 写出每项简短理由
4. 如条件允许，用独立会话/子 agent 跑测试 prompt
5. 汇总 baseline 分数

输出建议格式：

```text
Skill: xxx
总分：78/100
最低分维度：边界条件覆盖、指令具体性
主要问题：
- ...
- ...
```

### Phase 2：单轮改进
1. 锁定一个最低分维度
2. 提出一个具体改动
3. 编辑 skill
4. 重新评分
5. 对比改前改后

如果新分更高，保留。
如果新分没有更高，回退这轮思路，换下一个策略。

### Phase 3：验证
优先级如下：
1. 独立子 agent / 独立会话验证
2. 同环境下对照验证
3. dry-run 推演（最低配）

验证时要回答三个问题：
- 用户意图是否更容易完成了？
- 输出是否更稳了？
- skill 有没有带来新的负担或副作用？

### Phase 4：人工确认
在下列情况应暂停给用户看：
- 一个 skill 完成一轮有效改进后
- 准备进入下一轮大改前
- 准备从单个 skill 扩展到批量 skill 时

展示内容：
- 改了什么
- 分数变化
- 是否做了实测 / dry-run
- 建议继续还是停止

## 优化策略优先级

### P0：实测问题
- 带 skill 反而更差
- 输出偏离用户意图
- 格式和流程引导不稳定

### P1：结构问题
- description 不会触发
- workflow 顺序混乱
- 缺关键确认点

### P2：具体性问题
- 话太虚
- 没有输入输出说明
- 缺示例或失败处理

### P3：可读性问题
- 太长
- 重复
- 信息埋得太深

---

## 约束

1. 不改变 skill 的核心用途
2. 不擅自引入安装命令或新依赖
3. 不一次改多个核心维度
4. 不把 skill 改成巨长文档，默认控制在原体量 150% 以内
5. 任何“效果提升”都应尽量验证，不能只凭感觉宣布成功
6. 如果无法独立验证，要明确写明 `dry_run`

## 在 OpenClaw 里的建议用法

### 只评估
用户说：“评估一下这个 skill”

执行：
- 读 skill
- 建测试 prompt
- 给 8 维评分
- 输出问题列表
- 不直接改

### 评估 + 单轮优化
用户说：“帮我优化这个 skill”

执行：
- 先 baseline
- 再只改一轮
- 做验证
- 给出改前改后对比

### 小范围批量优化
用户说：“把这几个 skill 都看看”

执行：
- 先做批量 baseline
- 按分数从低到高排优先级
- 一次只真的动 1 到 3 个

## 与原版的主要差异

- 原版偏 Claude Code skill 生态，这里改为 OpenClaw / workspace 导向
- 原版强调 `.claude/skills/`，这里不绑定 Claude 目录
- 原版大量使用 git ratchet 表达，这里保留思想，但允许更轻量执行
- 原版展示页与宣传素材不参与核心运行，只作为参考资料

---

## 成功标准

当一次 Darwin 流程结束后，至少应得到以下其中之一：
- 一个更清晰、更稳、更易触发的 skill
- 一份清楚的 baseline 评估，知道问题在哪
- 一次被验证过的改进，而不是“看起来好像改好了”

如果都没有做到，就别硬说优化成功。
